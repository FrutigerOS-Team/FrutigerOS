Contributing

FrutigerOS welcomes code, design, documentation and testing contributions. The bar is simple: be truthful about what works.

Ground rules

  • Follow the Code of Conduct.
  • Keep changes focused. One coherent change per pull request.
  • Do not replace working code with placeholders, and do not mark a roadmap item complete without a reproducible check.
  • Never run destructive disk operations in tests, CI or examples.
  • Match the surrounding style; run cargo fmt before submitting.

Before you open a pull request

# in every crate you touched
cargo fmt --check
cargo test

# applications workspace
cd aero-apps
cargo fmt --all --check
cargo test --workspace

# ISO profile
cd frutigeros-iso
./build.sh --check

If a check cannot run in your environment (for example mkarchiso is unavailable), say so in the pull request and describe what you verified instead.

Commit style

Use the imperative mood and a scoped prefix when useful:

aerowm: forward pointer button events to surfaces
aeroshell: render panel clock with bitmap font
installer: add gated sgdisk/mkfs command planner
docs: add troubleshooting guide

Documentation changes

This site is plain HTML, CSS and JavaScript with no build step. Edit the page directly and verify it in a browser. Every page shares the same sidebar and top bar; keep links relative so the site works from file:// as well as a static server.

cd frutigeros-docs
python3 -m http.server 8080
# open http://localhost:8080/

Reporting bugs

Include the component, exact command, expected vs actual behaviour, and the relevant log lines. For compositor bugs, include the WAYLAND_DISPLAY value and whether you ran nested or on hardware. For installer bugs, state whether you used dry-run or --apply --yes — never include a bug report that asks someone else to reproduce a destructive run.

Security. Report vulnerabilities privately as described in SECURITY.md rather than in a public issue.
