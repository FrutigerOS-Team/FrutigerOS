Applications

Nine first-party applications live in the aero-apps Cargo workspace. Their data layers and backends are implemented and tested; interactive UI work is ongoing.

Status. The crates compile and their 32 unit tests pass, but most binaries still print a status summary instead of presenting a window. Treat this page as an inventory of backend capabilities, not a promise of finished apps.

Build the workspace

cd aero-apps
cargo build --workspace
cargo test --workspace

Each crate is a standalone binary. Run one directly, for example:

cargo run -p aero-files
cargo run -p aero-monitor
cargo run -p aero-terminal

Design conventions

  • No GUI toolkit dependency yet. Backends are plain Rust so they can be tested headlessly and reused by a future Aero Glass UI.
  • Read-only by default. System-changing operations (package install, disk writes, screenshot capture) are explicit and logged.
  • XDG paths. Config and state use XDG_CONFIG_HOME / XDG_DATA_HOME with sensible fallbacks.
  • Testable seams. Parsing, planning and formatting are separated from process spawning and filesystem mutation.

AeroTerminal internals

The terminal backend uses a pseudo-terminal pair: the child runs in the slave, the UI reads and writes the master. The VT parser handles printable characters, newlines, carriage returns and a minimum set of escape sequences. Resize propagates TIOCSWINSZ to the child.

pub fn pty_resize(fd: RawFd, rows: u16, cols: u16) -> io::Result<()>;

AeroMonitor internals

CPU utilisation is computed from the delta between two /proc/stat samples; memory comes from /proc/meminfo; disk usage uses df. The sampler is stateless between calls, so the UI owns the previous sample.

AeroScreenshot internals

Capture shells out to grim (Wayland) and optionally wl-copy for the clipboard. The backend builds the argument vector without a shell, so output paths with spaces are safe. A UI and a region-selection overlay are still pending.
